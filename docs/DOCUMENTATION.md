# Documentation strategy

InsightDock Charts uses the same approach as modern C++ open-source libraries in 2025–2026:

| Layer | Tool | Role |
|-------|------|------|
| **Source comments** | Doxygen-style `///` and `@brief` | IntelliSense/clangd **and** doc generators (portable) |
| **API reference (primary)** | [MrDocs](https://mrdocs.com) | Clang-based C++ reference (C++ Alliance; active OSS alternative to Doxygen-only workflows) |
| **Guides & site** | [MkDocs Material](https://squidfunk.github.io/mkdocs-material/) | Quick start, examples (source + rendered output), comparison — `mkdocs.yml` + `docs-site/`. Built and published to GitHub Pages by `.github/workflows/docs.yml` |
| **API reference (fallback)** | Doxygen | Optional; still used by many established projects |

## Why not Doxygen-only?

Doxygen remains widely deployed (Qt, LLVM docs history, many libraries), but **new C++ OSS** increasingly uses **Clang-based** generators that understand modern C++ (concepts, modules, accurate overload resolution):

- **MrDocs** — C++ Alliance, Clang/LLVM, presented at CppCon 2025, actively developed
- **hdoc** — compiler-based, Doxygen-comment compatible (another modern option)

InsightDock Charts standardizes on **MrDocs for API reference** because it matches current C++ community direction while our existing header comments stay valid.

Comment syntax stays **Doxygen-compatible** so tools agree: MrDocs, hdoc, Doxygen, and IDE hover all read the same `@brief` / `@param` blocks.

## IntelliSense (today)

Headers use Doxygen-style comments. **clangd** needs a compilation database — false errors like `file not found` or `Use of undeclared identifier 'std'` mean clangd is not configured yet (not real build failures).

```bash
./scripts/setup_clangd.sh
```

Then **reload the IDE window** (Cursor: Command Palette → “Developer: Reload Window”).

This generates `build/compile_commands.json` (core + PoDoFo when available) and uses [`.clangd`](../.clangd).

## Generate API reference (MrDocs — recommended)

```bash
# 1. CMake export for accurate parsing
cmake -B build -DCMAKE_EXPORT_COMPILE_COMMANDS=ON -DINSIGHTDOCK_BUILD_EXAMPLES=ON
cmake --build build

#    Example: download release and add to PATH
#    mrdocs only ships x86_64 Linux binaries — scripts/ci_docs_mrdocs.sh
#    (used by the docs GitHub Actions workflow) runs directly on the
#    x86_64 ubuntu-latest runner, no container/emulation needed.

# 3. Stock mrdocs ships with no CSS at all (plain browser-default styling).
#    Copy the repo's themed wrapper over the installed one before generating
#    (every time — mrdocs's own copy doesn't persist your edits):
cp docs/mrdocs-theme/wrapper.html.hbs \
  "$(dirname "$(command -v mrdocs)")/../share/mrdocs/addons/generator/html/layouts/wrapper.html.hbs"

# 4. Generate HTML reference
cd docs
mrdocs mrdocs.yml
# Output: docs/reference/
```

`scripts/ci_docs_mrdocs.sh` does the same theme copy automatically for CI runs.

Open `docs/reference/index.html` locally, or run the `docs` GitHub Actions workflow to publish it as part of the MkDocs site on GitHub Pages.

## Optional: Doxygen fallback

For teams that already run Doxygen in CI:

```bash
doxygen docs/doxygen/Doxyfile
# Output: docs/doxygen/html/
```

## Build the full site (MkDocs Material + embedded API reference)

`docs-site/` is the MkDocs markdown source: `index.md`, `getting-started.md`, `concepts.md`
(architecture/extension points), `guides/` (usage, PDF reports, troubleshooting — `guides/usage.md`
transcludes `docs/API.md` directly so there's one source of truth), `chart-types/` (one page per
chart type with full options), `examples.md`, `comparison.md` (transcludes `docs/COMPARISON.md`),
and `changelog.md` (transcludes `CHANGELOG.md`). `mkdocs.yml` lives at the repo root with
`docs_dir: docs-site`.

```bash
# 1. One-time: venv + MkDocs Material
python3 -m venv .venv-docs
.venv-docs/bin/pip install -r requirements-docs.txt

# 2. Generate the MrDocs API reference first (see above) — required input
cd docs && mrdocs mrdocs.yml && cd ..

# 3. Assemble + build: copies docs/gallery/*.png and docs/reference/ into
#    docs-site/, then runs `mkdocs build`
./scripts/build_docs_site.sh

# Preview locally
.venv-docs/bin/mkdocs serve   # http://127.0.0.1:8000
```

Output: `site/` (gitignored, rebuilt from sources each time — `docs-site/api/`
and `docs-site/img/gallery/` are themselves generated by the script, not
hand-maintained).

Known seam: `api/` is raw MrDocs HTML (themed via `docs/mrdocs-theme/`, not
MkDocs-rendered), so it doesn't carry the Material nav chrome — clicking
"API Reference" leaves the site frame. Acceptable for now; revisit if it's
worth bridging.

Built and published to GitHub Pages via `.github/workflows/docs.yml` (manual dispatch). See
`FUTURE.md` for what's still aspirational (online code generator, agent/skill docs).

## Maintaining docs

- Update **header comments** when changing public API (single source of truth).
- Regenerate **MrDocs** before releases.
- Do not duplicate symbol lists in Markdown; link to generated API pages instead.
