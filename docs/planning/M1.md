## Definition of done

An implementation issue closes after its acceptance criteria are satisfied, the implementation
and user documentation are merged, and relevant tests pass for the reviewed revision. Link the
PR and test evidence. A completed local change remains in review until merged.

Release tasks also require evidence from the actual release candidate: remote platform/feature
CI runs, fresh API generation, the reproducible archive and checksums, a clean installed consumer,
and verified publication links. An issue count or successful local build does not replace these
gates. The required platform/feature checks must pass before tagging the candidate.

Record a vcpkg submission separately from upstream acceptance/registry availability. A submitted
port can satisfy the submission criterion while upstream acceptance remains pending; do not
advertise registry installation until verified. Any change to the original M1 scope must be an
explicit maintainer decision in the parent issue and roadmap, with rationale and a destination.

## GitHub setup and maintenance

Published now: the M1 parent, its 14 linked work issues and four deferred trackers. The parent uses
linked task lists; native sub-issue relationships, repository milestone objects, labels and a
Projects board have not been created. The connected GitHub app exposes issue operations but not
milestone/Project administration. Local `gh` authentication was unavailable during the
initial planning pass; administrative setup remains a separate follow-up.

When administrative access is available, create one active milestone, **M1 — reliability and
release readiness**, associate issues #5–#19, and leave its due date unset. Add a single public
Project, **InsightDock Charts delivery**, with these views:

- **M1 delivery:** only active M1 work, grouped by Status.
- **Backlog:** deferred trackers and unscheduled proposals.
- **Release gates:** packaging, CI, artifacts and final acceptance work.

Use Status values Backlog, Ready, In progress, In review and Done; track blocking dependencies
separately. Useful fields are Priority, Area, Owner and evidence/PR links. Keep only one focused
implementation in progress per owner. Add a small set of type/area labels only when they help
triage. Native sub-issues can replace the parent task list while preserving the existing issue IDs.

Do not bulk-create version milestones for every long-term ambition. Once a real release version
is selected, put committed work into that release milestone and retain M1–M4 as strategic trackers.
Before each release, review remaining blockers and the exact candidate evidence. After release,
update support/upgrade documentation and reconcile the high-level roadmap.

## Practices researched

This is a lightweight adaptation for this repository, not a claim that all projects use the same
workflow:

- [Matplotlib's release guide](https://matplotlib.org/devdocs/devel/release_guide.html) uses version
  milestones, a release branch/feature freeze, candidate testing, documentation and artifact steps.
- [NumPy's roadmap](https://numpy.org/neps/roadmap.html) keeps broad strategic investment areas;
  [NEP 0](https://numpy.org/neps/nep-0000.html) uses reviewed design proposals for major changes
  while allowing small enhancements through ordinary PRs.
- [GitHub milestones](https://docs.github.com/en/issues/using-labels-and-milestones-to-track-work/about-milestones)
  group issues/PRs; [Projects](https://docs.github.com/en/issues/planning-and-tracking-with-projects)
  provide filtered views of that work; [sub-issues](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/adding-sub-issues)
  support parent/child planning.
